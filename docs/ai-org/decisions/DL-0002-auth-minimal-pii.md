# DL-0002 · 인증·개인정보 최소화

- 상태: **AMENDED (2026-07-12 — 구글 소셜 허용으로 개정)**
- 날짜: 2026-07-05 (개정 2026-07-12)
- 결정권자: Fable (사용자 질문에 대한 응답 + 판정)

## 개정 (2026-07-12, 사용자 지시)
사용자가 구글 로그인 연동을 요청 → 원 결정의 "소셜 제거"를 **구글만 허용**으로 개정:
- **구글 OAuth 허용**(UX: 간편 로그인). X(트위터) 로그인 버튼은 제거(범위 밖). 이메일+비밀번호 경로는 유지.
- PII 원칙은 그대로 — 구글에서 받는 것도 이메일+표시명 수준. 실명·전화 미수집.
- 근거 변화: "소셜 제거"가 PII 최소의 한 방법이었으나, 자캐 유저의 실사용 편의(구글 원클릭)가 더 큰 가치라는 사용자 판단. 헤드라인 방어는 여전히 Tier 0(RLS·클라 신뢰 제거, 이미 봉합)이므로 구글 추가가 보안 등급을 낮추지 않음.
- 실행: 로그인 페이지 X 버튼 제거·구글만, `supabase/config.toml`(site_url·redirect·google provider), 설정 가이드 `docs/google-oauth-setup.md`. 구글 앱 등록·시크릿은 사용자.
- 매직링크(원 결정 2번)는 미도입 상태 유지(선택 사항, 강제 아님).

## 문제
사용자 질문: "구글/카카오 등 PII 많은 소셜 로그인을 꼭 써야 하나? 아이디·비번, 많아야 이메일만으로 안 되나? 바이브코딩 사이트 보안 우려 분위기라."

## 현황 (FACT)
페어리는 **이미 이메일+비밀번호(Supabase Auth)가 주 플로우**다:
- `src/app/(main)/login/page.tsx:193` signUp(+이메일 인증), `:216` signInWithPassword, `:152` 비번 복잡성 검증.
- `src/app/(main)/reset-password/page.tsx:51` 이메일 재설정.
- `login/page.tsx:115` signInWithOAuth 는 **선택 추가**.
즉 최소-PII 경로는 이미 구축돼 있고 소셜은 떼면 그만.

## 가정
- 자캐 팬덤은 가명·익명 문화([../strategy-genome.md](../strategy-genome.md) §2).
- PII 최소화 = 유출 시 피해 반경·PIPA 부담 축소.

## 반박 (자기검증)
- "아이디/비번(이메일 없이)이 더 최소 아닌가?" → ❌. 이메일 없으면 복구 경로 상실(비번 분실 = 계정 상실) + 자체 인증 롤유어오운 위험. **이메일 기반이 최소이면서 안전.**
- "이메일+비번을 직접 구현하면 위험?" → Supabase Auth가 해싱·검증·리밋·재설정을 관리하므로 롤유어오운 아님. 안전.
- "로그인 방식이 보안의 핵심인가?" → ❌. **핵심 오해.** 실위험은 (a) 자체 인증 롤유어오운(회피됨), (b) 클라이언트 신뢰(C-1/C-3/C-4), (c) RLS 구멍(C-1/H-1). 로그인 바꿔도 이 셋이 그대로면 안전하지 않다.

## 결정
1. **이메일 기반을 기본·유일 권장.** Google/Kakao/Naver 소셜 제거 or 기본 미노출.
2. **권장: 이메일 매직링크/OTP(passwordless, `signInWithOtp`)** — 비번 미저장(유출·재사용·리셋 리스크 0), PII는 이메일 1개. (비번 방식 유지도 OK.)
3. iOS 앱 심사 요구 시에만 **Apple("Hide My Email")** 예외.
4. **PII 최소 원칙**: 이메일 + 표시명(핸들)만 수집. 실명·전화·생년월일·성인인증 미수집(성인 콘텐츠 도입 전까지 defer).
5. 최소-PII는 "피해 반경 축소"로 가치 있으나 **헤드라인 방어는 Tier 0**(RLS·클라이언트 신뢰 제거)임을 명심.
