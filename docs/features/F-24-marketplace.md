# F-24 마켓플레이스(marketplaceStore)   [demo(C-4)]

**WHAT**: 틀/자료의 판매·구매 거래 관리. `src/stores/marketplaceStore.ts`(339줄).

**현재상태**: demo(FACT, C-4). `COMMISSION_RATE = 0.2`(104-105행대, 20% 수수료 하드코딩). `recordSale()`(196-217행대)는 스토어 API에 정의(90행대)돼 있으나 **저장소 전체에서 호출처 0건 — 완전한 죽은 코드**(메타 발견에 명시된 "recordSale 죽은코드" 사례). 실제 표시되는 판매 데이터는 `generateDemoSales()`(121-152행대)가 `onRehydrateStorage`(310-314행대)에서 생성하는 가짜 데이터. `requestPayout()`(224-243행대)은 서버 검증 없이 무조건 `status:'pending'` 요청 객체를 생성해 즉시 반환 — 잔액 위조 후 정산요청을 막을 방법이 없음.

**스펙정합**: 06-database-schema.md의 sales/payout 테이블 스펙과 클라이언트 구현 사이 완전 괴리 — "판매 기록"이라는 개념 자체가 서버에 닿지 않는 클라이언트 전용 시뮬레이션.

**문제·리스크**: **C-4(치명)** — 가짜 `Sale{netAmount:1억}`을 localStorage에 직접 주입 후 `requestPayout()` 호출 시 존재하지 않는 매출로 출금 요청이 그대로 성립(감사 §5 해커 관점 확정 익스플로잇 #3). `recordSale` 죽은 코드는 "실제 판매가 발생해도 기록될 경로가 없다"는 의미이기도 함 — 반대 방향 버그(정당한 판매도 기록 안 됨).

**Fable판정**: **수정 — 서버검증**. 단, 이 수정은 **결제 백엔드가 먼저 성립해야** 의미가 있음 — 결제 없이 서버검증만 추가하면 검증할 실 거래 자체가 없음.

**다음작업**:
1. **(결제 백엔드 선행 후)** `recordSale`을 실제 결제 완료 웹훅에서 호출되도록 배선, `requestPayout`을 서버(Edge Function/RLS 강제 테이블)에서 잔액 검증하도록 재구현 — AC: 위조된 클라이언트 잔액으로 정산 요청 시 서버측 거부. (Opus)
2. 그 전까지는 `requestPayout` UI에 "정산 기능은 준비 중" 명시해 사용자가 실제 출금 가능하다고 오인하지 않도록. (Sonnet, 즉시 가능한 임시조치)

**의존·순서**: **선행조건**: 결제 백엔드(Toss 등) 구축(TOP50 #6). 그 전엔 본작업 defer, 2번 임시조치만 즉시 진행 권장. **후행영향**: F-25(정산 대시보드)가 이 스토어의 정직한 데이터에 의존.
