# F-23 작업물 공유(share)   [hook은 real·최고품질이나 정적export가 죽임]

**WHAT**: 완성 작업물의 공유 링크 생성·조회. `src/hooks/useShareWork.ts`(566줄, 직접 확인 — 감사 원문 "567줄"과 오차 1행 이내로 사실상 일치), 라우트 `src/app/(main)/share/[shareId]/page.tsx`(53줄).

**현재상태**: 코드 품질 자체는 real·최고 수준(FACT) — useShareWork.ts는 감사 대상 중 손꼽히는 완성도. 그러나 `share/[shareId]/page.tsx`:5-8의 `generateStaticParams()`가 `[{ shareId: 'demo' }]` 단 하나만 반환 — **실제 생성된 공유 링크는 전부 정적 빌드에 없는 경로라 404**. OG(Open Graph) 메타데이터도 이 이유로 항상 일반(generic) 값만 노출(개별 작업물 미리보기 카드가 SNS에서 절대 안 뜸).

**스펙정합**: 공유 기능 스펙(친구에게 작업물 공유) 자체와 훅 구현은 정합. 정적 export 아키텍처가 이 정합성을 무력화 — "구현은 맞았는데 배포 방식이 틀림"의 전형(감사 §13 "틀린 곳에 만듦" 테마의 직접 사례).

**문제·리스크**: **Critical(경쟁 공격점, 감사 §4 명시)** — 사용자가 작업물을 트위터에 공유해도 링크가 안 열림(바이럴·유입 구조적 차단). 이 자체가 페어리의 "공유하기 쉬운 창작 플랫폼" 가치 제안을 정면 부정.

**Fable판정**: **수정 — 런타임 결별에 종속(Tier 0)**. 훅 코드는 건드릴 필요 없음(재설계 금지) — 순수하게 라우팅/배포 방식 문제이므로 정적 export 결별 결정이 나온 뒤에 처리.

**다음작업**:
1. 정적 export 결별(Vercel ISR/서버 런타임 or SPA catch-all) 결정 대기 — 결정 후 `generateStaticParams` 제거 또는 동적 fallback 방식으로 전환 — AC: 임의 shareId로 접근 시 실제 작업물 렌더, OG 태그가 해당 작업물 고유 정보 반영. (Opus, 라우팅 아키텍처 변경 수반)
2. (결별 결정 전 임시조치, 선택) 공유 시도 시 "현재 공유 링크는 앱 내 이동만 지원됩니다" 같은 정직한 안내 — 완전 해결은 아니나 사용자 혼란 최소화. (Sonnet, 저비용)

**의존·순서**: **선행조건**: 정적 export 결별 결정(TOP50 #4·#5). F-15(templates/[id])·F-22(creator/[username])·F-13(collab/[code])과 동일 근본 원인 — 한 번의 라우팅 아키텍처 결정으로 4개 기능이 동시에 풀림(일괄 처리 시 효율 최대).
